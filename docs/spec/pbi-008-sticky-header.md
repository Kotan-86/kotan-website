## 目的(Why)

プロダクトゴール「初対面の人やオンライン上で交流する人が、僕自身の身の丈に合った前向きな印象形成をスムーズに構築できる状態にする」([docs/product-goal.md](../product-goal.md))に対して、現在のページは、ヒーローの下に4つのセクション(趣味・日常、活動歴、僕のコミュニケーション方法、いま考えていること・これから)が縦に並んでいる。

- セクションが4つに増えて縦に長くなっている状態だと、プロフィールサイトに載っている情報の見通しを立てにくい。〔出典: issue #10 の Why〕
- それによって、プロフィールを最後まで読まないと話題を出しにくい状況が起きる。〔出典: issue #10 の Why〕
- そのため、ぱっと見でどういう情報があるかが見通せて、興味あるセクションをすぐ読めるようにしたい。〔出典: issue #10 の Why〕

### POの意図(確認済み)

出典1: GitHub issue #10 の本文(作成者 = PO 本人)。**spec-designer は issue を直接取得していない**(ネットワークにアクセスしないため)。以下は main 経由で受領した本文による。

- **Why**: 上記「目的(Why)」のとおり。
- **位置**: ヒーローの上にヘッダーとして作る。
- **幅**: ヘッダーそのものの幅は、画面の幅いっぱいでよい。ただし、コンテンツを載せる範囲は、ヒーローや各セクションの両端にする。
- **常時表示**: ヘッダーは、ページ全体がスクロールされても常に表示される。
- **左端**: 「こーたんプロフィールサイト」と載せる。フォントサイズ 14px(レスポンシブ対応。640px 以上の場合)、フォントは Noto Sans JP。
- **4項目**: 各セクションを横一列に置く: 趣味・日常 / 活動歴 / 僕のコミュニケーション方法 / いま考えていること・これから。各セクションのフォントサイズは 14px(レスポンシブ対応。640px 以上の場合)。
  - issue 原文は4項目を「**中央**」に置くとしていたが、**PO の決定 Q2(2026-09-25)で「下段に4項目を左寄せ」に上書きされた**。本書は上書き後の意図(左寄せ)に従う。〔出典: sprint-backlog.md「POの決定(2026-09-25)」Q2〕
- **アイコン**: それっぽいものを入れる。可能であれば astro-icon(`npm i astro-icon`)を利用する。例: 趣味・日常 = `cbi:hobby`、活動歴 = `material-symbols-light:search-activity`、僕のコミュニケーション方法 = `material-symbols-light:communication`、いま考えていること・これから = `codicon:thinking`(issue の記載例は `import { Icon } from 'astro-icon'`、`<Icon name="mdi:account" />`)。
  - **issue の例のうち `cbi:hobby` と `codicon:thinking` は、PO の決定 B-1(2026-09-25)で `material-symbols-light` の別のアイコンに差し替えられた**。本書は差し替え後の意図に従う。〔出典: 下記 出典4、sprint-backlog.md「POの決定(2026-09-25)」B-1〕
- **小さい画面**: レスポンシブで小さくなる時は、アイコンのみを横一列に表示する。
- **フォーカス**: カーソルがフォーカスすると、アンダーラインが出る。
- **クリック**: クリックすると、当該セクションの見出しがページ上部に来るようにスクロールされる。
- **ヒーローの余白**: ヒーローの上にある余白(ヒーローボックス中にある上余白)は、下余白と揃える。

### 構造(ビルド成果物)

1. **ヘッダーがヒーローより前にある**: ビルド成果物の HTML で、`header` 要素がちょうど1つあり、文書の順で、ヒーローの `h1` より前にある。`header` 要素は `main` 要素の中に無い。〔検証: AI実行(`npm run build` の出力 HTML を読む)〕
2. **タイトルの文言と種類**〔Q10〕: `header` の中に、テキストが「こーたんプロフィールサイト」と完全に一致する要素が1つある。この要素は見出し要素(`h1`〜`h6`)でも、リンク(`a`)でもない。〔検証: AI実行〕
3. **ナビゲーションと4つのリンク**: `header` の中に `nav` 要素が1つあり、支援技術から読み取れる名前(例: 「ページ内の目次」。文言は実装判断)を持つ。`nav` の中にリンク(`a`)がちょうど4つあり、文書の順に、各リンクの支援技術から読み取れる名前が、4つの見出しの文言とそれぞれ完全に一致する。〔検証: AI実行(HTML を読み、`aria-label` またはリンク内のテキストを確かめる)〕
4. **リンク先が各セクションである**: 4つのリンクの `href` は、それぞれ同じページの中の1つの要素(`#<名前>`)を指し、指す先は、対応する見出しの `h2` 自身か、その `h2` を含むセクションである。4つの名前は互いに異なり、ページ内で重複しない。`href` に `/kotan-website/` 以外のサイト外へのパスを含まない。〔検証: AI実行〕
5. **見出しの構造が変わらない**: 見出し要素を文書の順に並べると、`h1`(1つ。「こーたん（齋藤 光貴）」)→ `h2`「趣味・日常」→ `h3`(4つ)→ `h2`「活動歴」→ `h3`(7つ)→ `h2`「僕のコミュニケーション方法」→ `h3`(3つ)→ `h2`「いま考えていること・これから」→ `h3`(3つ)で、`h4`〜`h6` は無い。ヘッダーの中に見出し要素は無い(PBI-007 AC-4 を引き継ぐ)。〔検証: AI実行〕

### 設計メモ(実装者への申し送り。実装方法の指定ではない)

- **PBI の大きさ**: [CLAUDE.md](../../CLAUDE.md) の基準は「PBI全体で3コミット程度、1コミットあたりの実装コード変更 300 行まで」。見込みは、ヘッダーのコンポーネント(60〜90行)、`index.astro`(10〜20行)、`BaseLayout.astro`(5〜15行)、`global.css`(0〜10行)、4つのセクションのコンポーネント(各 1〜3行)、`astro.config.mjs`(0〜15行)、`package.json`(0〜5行)で、**合計 100〜170 行、2〜3コミット**(未確認: 既存ファイルの行数からの見積もり。feasibility(1回目)の見積もりは約 110〜180 行、2〜3コミット)。基準に収まる見込み。`package-lock.json` の差分は、300 行に**数えない**(PO 確定: 解釈確認 3)。
- **実装の最初に確かめること(B-2。PO の決定の範囲外の注意点)**: B-2 は PO の決定の対象ではなく、PO の決定 Q7(Astro の組み込みのフォント機能で読み込む)が実現できるかどうかの前提である。実装の**最初のタスク**として、次の3点を実ビルドで確かめ、結果をタスクノートに記録する。
  1. Astro の組み込みのフォント機能で、Noto Sans JP の**日本語の文字**(ヘッダーに載る全角の文字)が取得され、表示に使われる(既定の文字の範囲 `latin` だけでは足りない恐れがある。feasibility)。
  2. 太さ **700**(タイトル)と **400**(項目名)の両方が取得される(既定は 400 だけ。feasibility)。
  3. `npm run build` が成功し(AC-27)、出力されるフォントのファイルの数・大きさを記録する。
  - いずれかを Astro の組み込みのフォント機能で実現できない場合は、**PO の決定 Q7 の範囲外**になる。その時点で実装を止め、`needs-decision` として PO に判断を戻す(代替の例: 閲覧時に外部から読み込む / フォントの npm パッケージを追加する。どちらも AC-26 に関わる)。実装者の判断で代替に切り替えない。
  - フォントの提供元の選択(feasibility は、`japanese` のサブセットを持つ `fontsource` を示した)は、Astro の組み込みのフォント機能の中での選択であれば、実装者が決めてよい(レベル1)。
- **feasibility(1回目)で確かめたこと(2026-09-25)**:
  1. `astro-icon` は Astro 7 と互換ありと判断(実ビルドは未実行)。使えない場合は、PO の決定 Q3 に従い SVG ファイル(依存の追加なし)に切り替える(PO への再確認は不要)。
  2. issue の例の4つのアイコンは実在。利用許諾により B-1 で2つを差し替えた。差し替えの候補の実在は未確認(「spec-designer が具体化した点」)。
  3. フォント → 上の B-2。ビルドにネットワークが要る見込み → README に追記する(AC-28)。
  4. 幅 768px の下段は約 594px で収まる見込み(ブラウザ未観測。収まらない場合は、PO の決定 Q4 に従い境界を調整し、PO確認で判定する)。
  5. 1280 x 800px で「いま考えていること・これから」の見出しはヘッダーの下まで持ち上がらない見込み(AC-17 のただし書きで判定する)。
  6. リンク先の作り方(了承C の①/②)は、実装者の選択(feasibility は①を推奨)。
- **`src/env.d.ts`**: 変更してよい範囲の外である。astro-icon の型の参照などのために変更が要るとわかった場合は、自分で変更せず `needs-decision` を返す(feasibility N-8)。
- **スクロールの位置(AC-17・AC-18)**: 常に表示されるヘッダーの高さの分だけ、見出しが隠れないようにする必要がある。ヘッダーの高さが幅(767px 以下 / 768px 以上)で変わる見込みのため、両方の幅で確かめること。
- **ヒーローの上の空き(AC-20)**: 現在の上側の余白は、画面の高さに連動する式である(前提節)。Q1 の決定により、画面の高さに連動しない固定の空きになる。ヘッダーがページの流れの中に場所を取るか取らないかで、空きの測り方が変わるので、「ヘッダーの下端から」測って 48px になることを確かめること。
- **色(AC-25)**: アイコンの SVG が色を持つ場合も、表示時は本文色(トークン経由)になるようにする。Tailwind CSS v4 の自動ソース検出は仕様書も走査しうるため、ビルド済み CSS にクラスがあることを使用の証拠にしない(PBI-005 の feasibility F-3)。
