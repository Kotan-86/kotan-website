## 目的(Why)

プロダクトゴール([docs/product-goal.md](../product-goal.md))の2つ目(2026-09-25 策定)「社内外でこーたんの仕事やスキルを知ろうとする人が、アウトプットや発信を根拠に、現在のスキルや得意領域を具体的に把握できる状態にする」に直接つながる。

## 実現内容(What)

### ユーザーから見えるもの

1. 「活動歴」と「僕のコミュニケーション方法」の間に、見出し「アウトプット」のセクションが現れる。左端・最大幅・見出しの見た目・セクション間の余白は、他のセクションと同じ。
2. 見出しの下に、4つのフィルターチップ「すべて」「登壇」「ブログ」「ピッチコンテスト」が、この順に横一列に並ぶ。ページを開いた時点では「すべて」が選ばれている。
3. チップを選ぶと、そのカテゴリのアウトプットだけが表示される。「すべて」を選ぶと6件すべてが表示される。選ばれているチップは、基調色の地に白文字で、他のチップと見た目で区別できる。
4. チップの下に、アウトプットごとのリンクカード(白地)が並ぶ。並び順は issue #5 に書かれた順(絞り込んだときも、その順を保つ)。幅 640px 以上では2列、639px 以下では1列(JavaScript が無効のときは、幅にかかわらず1列。D-1)。2列のとき、表示中のカードを1件目は左、2件目は右、と交互に振り分け、左右の列のカードは上端を揃えず、各列の中でカードが上から 5px の間隔で詰まって並ぶ(石積み状)。列の間隔も 5px。
5. 各カードは、サムネイル(取得できた場合だけ)、題名、補足の文言からなる。題名と補足は issue #5 の文言(OGP のタイトル・説明は使わない)。カード全体がそのアウトプットへのリンクで、新しいタブで開く。
6. サムネイルを取得できなかったアウトプットは、サムネイルの無いカードとして表示される(空の枠や壊れた画像の表示は出ない)。
7. JavaScript が無効のときは、チップは表示されず、6件すべてのカードが、幅にかかわらず1列で、確定表の順に表示される(D-1)。
8. 固定ヘッダーは変わらない(「アウトプット」の項目は無い)。

### 運用(PO から見えるもの)

9. アウトプットを1件追加するには、アウトプットの定義(URL・カテゴリ・題名・補足)の1か所に1件を書き足して再ビルドするだけでよい。OGP の画像はビルドのたびに取得され、サイトに取り込まれる。
10. OGP の取得に失敗しても、ビルドは失敗しない。1件あたり 10 秒で打ち切る。失敗した URL は、ビルドのログに出る。
11. プロキシ環境でビルドするときは、`NODE_USE_ENV_PROXY=1` を付ける(Node 22.21 以降・24 以降)。付けないと、ビルドは成功するが、サムネイルなしになる(D-3。CLAUDE.md と README に記す)。

### spec-designer が具体化した点(承認済み。PO 承認 2026-10-08)

- 見出しと中身(チップの列)の間、チップの列とカードの間は、どちらも 24px(既存の「見出しと中身」の間隔と同じ)。
- 選ばれていないチップの枠は細い線(1px)とする。
- カードの角丸・内側の余白は、既存のカードと同じ(`rounded-2xl`・24px)。サムネイルはカードの上部に置き、元の縦横比を保ち、切り取らない。
- セクションには、リンク先の名前 `outputs` を付け、`src/data/section-ids.ts` に定義する(ヘッダーには加えない。別PBIでヘッダーに加えるときに使う)。
- 2列の振り分け(交互)は、絞り込み後の表示中のカードの順で行う(例:「登壇」を選ぶと、1件目と3件目が左、2件目が右)。

### 共有IF(複数のタスクにまたがりうるもの)

- **アウトプットの定義の形**: 各件が「URL、カテゴリ(「登壇」「ブログ」「ピッチコンテスト」のいずれか)、題名、補足」を持ち、定義の並びがそのまま表示の順(確定表の順)になる。OGP の取得の処理、セクションのコンポーネント、テストが共通に使う。
- **OGP の取得の結果の形**: 「サムネイルあり(サイトに取り込んだ画像)」か「サムネイルなし(+ 失敗の種類 ①〜⑤)」のどちらか。コンポーネントは、この結果だけを見てカードを描き分ける。
- **カテゴリの名前**: チップの表示文字列と、定義のカテゴリが一致すること(絞り込みの判定の基準)。
- **OGP の取得の処理の呼び出し形**: `fetch` を引数で受け取れる純関数とする(D-6。テストはスタブの `fetch` を渡す)。モジュール名と関数のシグネチャは、タスク分割時に確定する(test-writer の Red 用スタブのため)。

### 設計メモ(PO の決定に基づく実装の方針。受入基準ではない。承認済み。PO 承認 2026-10-08)

受入基準は結果で書いてあり、以下は実装の方針である。方針どおりにいかないときの扱いも併記する。

1. **画像の取り込み(D-2)**: まず、自前の `fetch` で画像を取得し、`public/` 配下の専用ディレクトリ(`.gitignore` の対象)に書き出して、サイトのパス(`base` を含む)で参照する方式を試す。**実装の最初に**、ページの描画中に書き出したファイルが `dist/` に載るかを確かめる。載らないときは、Astro の画像機能で取り込む方式に切り替え、`astro.config.mjs` の `image.remotePatterns` を https の全ホストの許可にしてよい(PO 了承済み。`astro.config.mjs` の変更はこの目的に限る)。この場合は、取り込みの前に自前の `fetch` で画像が取得できるかを確かめ、取得できない画像は画像機能に渡さない(画像の取得の失敗でビルドを落とさない。AC-12④)。どちらの方式を採ったかは、タスクノートに記録する。
2. **取得の処理の形(D-6、N-2)**: `fetch` を注入できる純関数にし、取得の結果を「サムネイルあり / サムネイルなし + 失敗の種類 ①〜⑤」の形で返す。打ち切りは1件 10 秒で、HTML の取得と画像の取得の合計(1件の取得全体で1つの打ち切り。PO決定 Q2「1件あたり 10 秒」の明確化。AC-32 の 20 秒未満と整合)。
3. **OGP の解釈(D-6)**: 依存を足さず自前で解釈する(Q10)。`meta` の属性の順に依存しない。`content` の値の HTML 文字参照(`&amp;` など)をデコードする(AC-31)。
4. **並列の取得(D-6)**: 全件を並列に取得する(AC-32)。
5. **開発サーバでのメモ化(D-6)**: `astro dev` では描画のたびにページの処理が走るため、取得の結果を開発サーバの起動中は使い回し、再読み込みのたびに取得し直さない。公開物には影響しないため、受入基準にはしない。
6. **2列の振り分け(D-1)**: HTML は平らな並びで出力し、閲覧時の JavaScript が、幅 640px 以上かどうかと、絞り込みの結果に応じて、左右の列へ振り分ける。チップは HTML に存在させ(AC-2)、JavaScript が無効のときは表示されない状態にしておく。絞り込みで非表示にしたカードは、支援技術にも出ない状態にする(AC-21)。
7. **色(N-5)**: 既存のトークン(カードの背景色、基調色、本文色)で足りる。トークンは追加しない(AC-19)。
8. **ヘッダー(参考)**: `SiteHeader.astro` が `section-ids.ts` の全項目を回して項目を作っていないかを、実装時に確認する(回していると、`outputs` を足しただけでヘッダーに5項目目が出て AC-26 に反する)。回している場合は、`SiteHeader.astro` を変えずに AC-26 を満たす方法が無ければ、`needs-decision` で返す。
